# Architecture - Project Bedrock

This is the architecture for InnovateMart's retail store sample app, deployed on Amazon EKS with managed AWS data services. I'll walk through each layer of the stack and explain how they connect.

---

## Overview

Traffic from the internet hits an AWS Application Load Balancer, which terminates TLS and forwards to the UI service running inside the cluster. The UI calls the other backend services internally using Kubernetes DNS. Each backend service owns its own data store, all of which are managed AWS services outside the cluster.

The cluster is named `project-bedrock-cluster` and runs Kubernetes 1.34. The node group uses two `t3.large` instances (Amazon Linux 2023) in private subnets, with a third available for auto-scaling. Nodes are on-demand.

---

## Network

The VPC (`10.0.0.0/16`) spans two availability zones, us-east-1a and us-east-1b, with one public and one private subnet each.

| Subnet | CIDR | AZ |
|---|---|---|
| Public | `10.0.0.0/20` | us-east-1a |
| Public | `10.0.16.0/20` | us-east-1b |
| Private | `10.0.32.0/20` | us-east-1a |
| Private | `10.0.48.0/20` | us-east-1b |

EKS nodes and RDS instances live in the private subnets. The ALB is placed in the public subnets, which are tagged with `kubernetes.io/role/elb=1` so the Load Balancer Controller can find them. Private subnets are tagged `kubernetes.io/role/internal-elb=1`.

Outbound internet access from the private subnets goes through a single NAT Gateway sitting in us-east-1a. There's one Elastic IP attached to it.

---

## Application Services

All seven services run as Deployments with ClusterIP Services in the `retail-app` namespace. They talk to each other using short DNS names like `http://catalog`, `http://orders`, and so on. The UI is the only service exposed outside the cluster.

The images are all from the AWS Containers public ECR gallery at version 1.6.1, except for RabbitMQ (`rabbitmq:3-management`) and Redis (`redis:7`) which are standard Docker Hub images.

The UI calls catalog, orders, carts, and checkout. Checkout depends on RabbitMQ and Redis. Catalog, orders, and carts each connect to their respective data stores.

Every application container is configured with a 100m CPU / 256Mi memory request and a 500m CPU / 512Mi memory limit.

---

## Data Layer

**Catalog** uses RDS MySQL 8.0 (`project-bedrock-catalog`, db.t3.micro, 20 GiB gp3). The security group only allows port 3306 from the EKS cluster security group, so it's not reachable from anything other than the nodes.

**Orders** uses RDS PostgreSQL 16 (`project-bedrock-orders`, db.t3.micro, 20 GiB gp3). Same setup, only port 5432 from the cluster SG is allowed.

Both RDS instances are in the private subnet group and are not publicly accessible. Neither has multi-AZ enabled (this is a capstone project, not production).

**Carts** uses a DynamoDB table (`project-bedrock-carts`) with on-demand billing. The hash key is `id` (string), and there's a GSI on `customerId` with ALL projection for customer-scoped queries.

Credentials for MySQL and PostgreSQL are generated by Terraform using `random_password` and stored in AWS Secrets Manager at `project-bedrock/catalog-mysql` and `project-bedrock/orders-postgres`.

---

## Secrets Management

Rather than hardcoding credentials or injecting them through values.yaml, I used External Secrets Operator to sync from Secrets Manager into Kubernetes Secrets. ESO runs in its own namespace and watches two `ExternalSecret` resources in `retail-app`.

`project-bedrock/catalog-mysql` syncs to a Kubernetes Secret named `catalog-db`, and `project-bedrock/orders-postgres` syncs to `orders-db`. Both refresh every hour. The catalog and orders pods then read the username and password from those secrets as environment variables.

ESO authenticates to AWS through a service account called `external-secrets-sa`, which has an IRSA annotation pointing to `project-bedrock-eso-role`. That role has a scoped policy (`project-bedrock-eso-read`) allowing only `GetSecretValue` and `DescribeSecret` on those two specific secrets.

---

## IAM and IRSA

No static AWS credentials exist anywhere in this system. Every pod that needs AWS access uses IRSA (IAM Roles for Service Accounts), which works through the cluster's OIDC provider.

There are three IRSA setups:

The **AWS Load Balancer Controller** uses `aws-load-balancer-controller` in `kube-system`, mapped to `project-bedrock-lb-controller-role`. This role carries the LBC IAM policy from `iam_policy.json`.

The **External Secrets Operator** uses `external-secrets-sa` in `retail-app`, mapped to `project-bedrock-eso-role` with the scoped Secrets Manager read policy.

The **Carts service** uses a `carts` service account in `retail-app`, mapped to `project-bedrock-carts-role`. This role allows the full set of DynamoDB operations on the carts table and its indexes.

The OIDC provider is managed by Terraform (`aws_iam_openid_connect_provider.eks`). Each role has a trust policy that pins the exact service account namespace and name using `StringEquals` conditions on the OIDC subject and audience claims.

---

## Ingress

The AWS Load Balancer Controller manages an internet-facing ALB from the `retail-ui` Ingress in `retail-app`. HTTP on port 80 redirects to HTTPS on 443. TLS is terminated at the ALB using an ACM certificate (`arn:aws:acm:us-east-1:927656030834:certificate/a0e3150a-83d7-439d-abc8-f5d3a0be2d65`). The target type is `ip`, so the ALB routes directly to pod IPs.

The ingress has two rules: one for the hostname `44-197-2-76.nip.io` and a catch-all for direct ALB DNS access. Both route to the `ui` service on port 80.

---

## Observability

The `amazon-cloudwatch-observability` EKS add-on is installed, which deploys the CloudWatch Agent as a DaemonSet and enables Container Insights. The node IAM role has `CloudWatchAgentServerPolicy` attached so the agent can write metrics and logs.

EKS control plane logs (api, audit, authenticator, controllerManager, scheduler) are all forwarded to CloudWatch.

---

## Asset Pipeline

There's an S3 bucket (`bedrock-assets-alt-soe-025-5437`) with all public access blocked. When an object is uploaded, S3 triggers the `bedrock-asset-processor` Lambda function. The Lambda is Python 3.12 and right now just logs the filename. The plan is to extend it for actual image processing. Its role has `AWSLambdaBasicExecutionRole` and nothing else.

---

## CI/CD

The GitHub Actions workflow uses OIDC to assume an AWS role, so there are no long-lived credentials in the repo. Any PR that touches `terraform/**` runs `terraform plan` and posts the output as a comment. Merging to `main` runs `terraform apply` automatically.

The role ARN is stored as the `AWS_ROLE_ARN` repository secret, set from `terraform output github_actions_role_arn`.

---

## Dev Access

There's an IAM user `bedrock-dev-view` for developers who need read access. It has `ReadOnlyAccess` managed policy, plus an inline policy allowing `s3:PutObject` on the assets bucket so they can upload files. For Kubernetes access, the user is mapped to the `bedrock-viewers` group via `aws_eks_access_entry`, and that group is bound to the built-in `view` ClusterRole through a `ClusterRoleBinding`.

---

## Remote State

Terraform state is stored in S3 at `bedrock-tfstate-alt-soe-025-5437`, key `project-bedrock/terraform.tfstate`, with versioning and AES256 encryption enabled and all public access blocked. State locking uses native S3 conditional writes (`use_lockfile = true`), which means no DynamoDB table is needed.
